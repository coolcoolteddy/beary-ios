# 日记位置 · 后端字段说明（批 E，2026-10-30）

> 本文件是 App 端批 E 的后端对接说明，**不是已执行的迁移**。本批不改生产库、
> 不改 worker.js（本仓库是 iOS 仓库，根本没有 worker.js；后端批拿到本文件后再执行）。
> App 端已先行透传字段：后端上线前，服务端忽略未知键时位置不持久化，
> 属于已知缺口，见末尾“上线前缺口”。

## 1. 数据模型（方案 A：只存文本，不存经纬度）

`entries` 表新增两列，均为可空文本：

```sql
-- D1 迁移（后端批执行，本批不执行）：
ALTER TABLE entries ADD COLUMN location_name TEXT;
ALTER TABLE entries ADD COLUMN location_district TEXT;
-- 注意：不要加 location_lat / location_lng / 任何坐标列。
-- 方案 B（地图专用坐标）须 Li 另行定夺，本批默认不开。
```

- `location_name`：精确地点文本（如 POI 名、街道门牌），作者本人与私密态可见。
- `location_district`：区级文本（如“鄞州区”），公开态他人可见的唯一位置信息。
- 两列都由 App 端在定位/搜索时从设备侧逆地理编码得出后随正文一起发出；
  服务端只做 trim 与长度上限（建议单列 ≤200 字），不负责再解析区级。

## 2. API

- 新建 `POST /beary/api/entries`：body 可带 `location_name` / `location_district`
  （缺省 = NULL；空串按 NULL 计）。
- 编辑 `PUT /beary/api/entries/:id`：两键三态——省略 = 保留原值；传值 = 覆盖；
  传显式 `null` = 清空（App 端改选/清除时两键算清后发出，不出现半更新）。
- 列表与单篇响应：凡返回日记行处一律透传两字段（与 `mood` / `weather` 同款透传口径）；
  **不要在服务端做截断脱敏**：脱敏在 App 展示层实时做（公开且 viewer 非作者时
  只渲染区级），公开翻回私密才能立即恢复精确值。服务端截断会永久丢失精确值。
- 可见性切换（visibility 接口）不碰位置字段；删除进回收站、恢复、彻底删除、
  用户注销均按日记行现有生命周期走，位置字段随行生死，不另建位置表、不留孤行。

## 3. 展示口径（App 端已实现，见 `BearyLocationDisplay.display`）

| 谁看 | 私密篇 | 公开篇 |
|---|---|---|
| 作者本人 | 精确地点名（无名退区级） | 精确地点名 + 橙色提示“公开后他人仅见区级（X）” |
| 他人 | 不可见（整篇占位） | 仅区级；无区级时整行不显示，绝不回退精确名 |

无位置（两字段双空）时卡片/详情不留空行。

## 4. 日记地图聚合（App 端已实现，见 `BearyLocationMap.groups`）

- 本人地图：按精确地点文本聚合，私密 + 公开都进，数字 = 该地点篇数。
- 他人地图：按区级聚合，只进有效公开篇，私密不进不计入，无区级不进。
- 地图打点按文本现场地理编码（MapKit），坐标只在 App 内存里，不写库、不缓存到盘。
- 聚合是日记列表的纯函数：可见性翻转/删除/回收站/注销的同步靠重拉列表后重算，
  不存在需要失效的地图缓存；App 不为地图加轮询。
